# Архитектурные решения и ограничения

Поля моделей описаны в [структурах данных](data-model.md), операции публичного API —
в [интерфейсах](interfaces.md). Здесь собраны причины устройства каталога и его границы.

## Эксперимент с Conan

Этот отдельный проект исследует Conan как хранилище Record и зависимостей.
Memory/Memgraph сохраняют полный графовый контракт; Conan реализует подмножество
через рецепты и встроенные lockfiles. Представления ищутся по координатам имени
и наличию точной зависимости в графе кандидата. Явные IMPLEMENTS не выводятся.

Conan CLI выбран из-за экспериментального статуса Python API. Общий индекс
обратных связей отсутствует: проверяются графы найденных кандидатов. Это существенная
стоимость эксперимента. Для проверки batch перед публикацией копируется Conan home.
Формат рецепта ограничен каноническими неконфигурируемыми рецептами.
Подробнее: [Conan](conan.md).

Следующие разделы о типизированных связях, транзакциях и резолвере совместимости
описывают полный контракт Memory/Memgraph. Conan использует собственный граф
и root lockfile; общая точка входа возвращает точный граф по умолчанию.

## Неизменяемый граф и пользовательское содержимое

Каталог отвечает за точные ссылки, связи и публикацию независимых JSON-снимков.
Схемы проектов, запусков и ресурсов принадлежат пользователю. Это позволяет хранить
разные виды объектов одной моделью Record без реестра пользовательских типов.

Опубликованная запись и все её исходящие связи неизменяемы. Новые объекты могут
ссылаться на существующие; дописывать исходящие связи старым объектам нельзя.
Такое правило сохраняет исходные требования конкретного релиза и служит основой
стабильного разрешения его зависимостей.

Ref и модели результатов — frozen dataclasses. Конструкторы остаются простыми;
проверки координат и структуры выполняются на границе каталога. JSON-преобразование
принадлежит самим моделям, а вложенное содержимое замораживается при публикации
и чтении. Пользовательский Python-класс не сохраняется и не загружается из базы.

## Правила графа

Причинный граф состоит из REQUIRES, USED и обратного PRODUCED; он ацикличен.
Для PRODUCED направление обращается при проверке: созданный объект зависит
от своего производителя, а производитель — от использованных объектов.
IMPLEMENTS не участвует в этой проверке циклов.

Совместимость проверяется отдельно: BACKWARD_COMPATIBLE_WITH соединяет версии
одного namespace/name/kind, допускает не более одного исходящего предшественника
и не содержит циклов. Совместимость — заявление автора версии; каталог проверяет
структуру цепочки, но не фактическую взаимозаменяемость содержимого.

## Разрешение версий

Резолвер читает исходный достижимый граф REQUIRES. Кандидаты — только версии этого
графа; промежуточные версии исходящих цепочек совместимости служат доказательством,
но не становятся кандидатами. Сравнение строк версий и диапазоны не используются.
Корневой Ref закреплён.

Используется жадный алгоритм: за проход разрешается только одно семейство версий.
Семейства с несколькими версиями рассматриваются по минимальному числу рёбер REQUIRES
от корня до любой версии семейства в текущем графе. При одинаковом расстоянии
порядок задаёт каноническая строка family: JSON-массив namespace, name и kind.
Версии внутри семейства упорядочены по расстоянию, затем по identity.

Выбирается первое семейство, в котором одна версия по цепочке совместимости заменяет
все остальные и не требует замены корня. Неразрешимые и закреплённые группы пока
пропускаются: они могут исчезнуть при сокращении других веток.
Зависимости вытесненных версий удаляются, входящие ссылки перенаправляются,
полные дубликаты связей объединяются и недостижимые вершины удаляются.
После каждой замены расстояния и порядок групп вычисляются заново.
Каждый успешный проход сокращает граф; уже выбранная старшая версия не понижается.

Поиск с возвратом не выполняется. Оставшиеся конфликты вызывают VersionConflict,
цикл после подстановки — DependencyCycle. Ошибка не доказывает отсутствие любой
допустимой комбинации: другой порядок решений иногда позволяет разрешить граф,
но алгоритм не пересматривает уже выполненные замены.

Например, если корень требует A1 и A2, A1 требует B2, а A2 — B1, сначала разрешается
ближайшее семейство A. Если A2 заменяет A1, ветка A1 удаляется вместе с B2,
и достаточно B1. До удаления ветки выбор B2 как замены B1 был бы преждевременным.

Для фиксированного Ref и одинаковых параметров результат или конфликт стабильны
после допустимого расширения каталога, переподключения и перезапуска. Доказательства
используют только неизменяемые исходящие цепочки; новые входящие связи не участвуют.
Стабильность графа не гарантирует неизменяемость внешних файлов и окружения инструментов.
Порядок публикации, порядок выдачи записей и связей backend и PYTHONHASHSEED
не влияют на выбор: приоритеты определяются самим достижимым графом и координатами.

Разрешённые связи производны и не записываются. Режим resolve_versions=False
возвращает исходный точный граф. Записи сортируются по идентичности, связи — по JSON.

## Чтение и хранение

CatalogGraph отделяет графовые операции от публикации и чтения записей в Catalog.
Backend управляет временем жизни транзакций: один обход, включая доказательства
совместимости, использует один снимок. Между отдельными вызовами снимок не сохраняется.

MemoryBackend хранит состояние в памяти под RLock. MemgraphBackend использует
обычные транзакции. Узел HCRecord содержит фиксированные координаты, ключ и JSON
всей записи; пользовательские поля не проецируются в свойства базы.
Индексируются только ключ и общие поля. Поиск по payload отсутствует.
Лимитов и пагинации нет: предполагается небольшой граф.

## Границы PoC

Предполагается один издатель каждого точного Ref. Конкурентные публикации разных
объектов, повторы и восстановление после сетевого сбоя координирует клиент.
Журнала публикаций, автоматических повторов и гарантии идемпотентности нет.
Старые форматы хранения не читаются и не мигрируются.

Файлы остаются во внешних хранилищах. Ресурсы файловой системы описываются абсолютными
путями; подготовка доступа к ним остаётся у пользователя. Материализация — отдельная
операция ресурса, которая не выполняется при чтении записи из каталога.
Git-кэш предполагает координацию доступа со стороны пользователя.

Порядок проверок и устройство тестового окружения описаны
в [документации разработки](development.md).
